# Trust: method, verification, and security

This document is the authoritative narrative and claim boundary for the production `/method`, `/verification`, and `/security` pages. It does not establish contractual terms, customer evidence, certifications, or a production AWS access policy.

Each Trust route resolves its next action inside the page. The shared global footer CTA is suppressed on these routes while footer navigation and identity remain present.

## Method

HKGpipi uses one operating chain: **Find → Validate → Assign → Change → Approve → Verify**.

- **Find:** identify economically meaningful AWS cost opportunities from permitted evidence.
- **Validate:** test usage, commitment, and engineering-risk context.
- **Assign:** connect work to the responsible workload, owner, and implementation location where identifiable.
- **Change:** define the engineering remediation.
- **Approve:** move work through the customer's existing engineering and change-control process.
- **Verify:** measure the post-deployment economic result against the agreed baseline.

Recommendations are inputs; verified reductions are outcomes. An opportunity must pass technical, economic, risk, ownership, approval, deployment, and measurement decisions. HKGpipi prepares and supports the work, but the customer retains production approval and deployment control.

Illustrative opportunity records must be visibly labelled and must never be presented as customer activity, live account data, or a measured customer result.

## Verification

- **Expected saving:** an estimate of the economic effect before an approved change is deployed.
- **30-day measurement view:** the observed post-change billing result during the current measurement context.
- **Verified annualised saving:** the measured post-change saving, normalised where required and expressed as an annualised value under the agreed verification basis.

Conceptually, baseline spend minus normalised post-change spend equals verified saving. The baseline and treatment of material workload-volume, unrelated infrastructure, pricing, commitment, or external architecture changes are agreed before outcome-based implementation begins.

A 30-day measurement view is not an end-to-end engagement promise, a universal workload duration, or a universally fixed contractual methodology. Outcome-based implementation remains 25% of verified savings under the agreed verification basis.

## Security and change control

Discovery is intended to use tightly constrained read-only AWS access. The exact engagement-specific policy is reviewed before access is granted. Discovery does not require unrestricted administrative access and does not grant HKGpipi independent production-deployment authority.

Implementation remains within the customer's engineering path: HKGpipi remediation → customer repository or ticketing process → customer review → CI/checks → customer approval → customer-controlled deployment.

Before AWS access is granted, the requested AWS permission scope, intended data categories, engineering-workflow boundary, and verification-access requirements must be available for review. The engagement-specific access model is reviewed before that access is granted.

Security certifications, retention commitments, data-residency terms, subprocessors, and formal assurance documents may be published only when established and approved. Their absence must not be converted into an implied claim.

## Public claim boundary

Do not fabricate or imply customers, results, case evidence, guarantees, certifications, endorsements, contractual mechanics, or assurance documents. Company narrative, customer proof, legal terms, final data-handling commitments, and a production access-policy artifact remain later-gate work.
